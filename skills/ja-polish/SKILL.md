# ja-polish

## Purpose

LLM の書く日本語は文法的には正しいのに読者に「機械が書いた」と伝わる。原因は語彙よりもリズムと定型だ。文長が揃い、文末が「〜ます。」で3連続し、冒頭に「はい、」、末尾に「いかがでしょうか」が付き、「することができます」「を行う」で水増しされ、逆接でない「〜ますが、」で文がつながる。

このスキルは4層で校正する。機械で拾えるものは機械に任せ、Claude は判断と書き直しに集中する。

| 層 | 何を直すか | 誰が |
|---|---|---|
| 表記 | 冗長表現、文長、読点数、ひらく漢字、全角半角 | textlint（`scripts/check.sh`） |
| 書式 | 「**重要**: 〜」型の箇条書き、絵文字リスト、太字の乱用 | textlint preset-ai-writing |
| 文体 | 定型句、ぼかし、語順と読点、逆接の「が」、名詞化、カタカナ語、文末のリズム | Claude（この SKILL.md と `references/patterns.md`） |
| 構成 | 意味が取れない、曖昧、前提が飛んでいる箇所 | tool を全部外した Haiku 読者（`scripts/check.sh` の reader） |

hook で自動適用はしない。モデルには自由に書かせ、ユーザーが校正を求めたときだけこのスキルが動く。

## Instructions

### 0. 対象と文体を決める

対象はユーザーが示した文章だ。ファイルなら読む。「さっきの回答を直して」なら直前の自分の返答が対象になる。

文体（レジスター）は入力と用途から推定する。迷うときだけ聞く。

| 用途 | 文体 | 目安 |
|---|---|---|
| チャット返信、技術記事、README | ですます | 前置きと締めの挨拶は削る |
| 仕様書、ADR、設計メモ | である | 事実と意見を分ける |
| コミットメッセージ、PR タイトル | 体言止め | `fix: ログイン時の null 参照を修正` |
| ビジネスメール | ですます | 二重敬語を禁止（ご確認いただけますでしょうか → ご確認ください） |

詳しくは `references/registers.md`。

### 1. 機械検査を先に走らせる

```bash
bash <skill dir>/scripts/check.sh <file>            # 表記・書式・リズム・読者 の4層を一括
bash <skill dir>/scripts/check.sh <file> --fix      # ひらく漢字などの自動修正を先に適用
bash <skill dir>/scripts/check.sh <file> --no-reader  # 短文や急ぎのときは読者を省く
```

対象がチャットの一部なら、いったんファイルに書き出してから渡す。初回は textlint を `~/.cache/ja-polish` に導入するため 1 分ほどかかる。以後はオフラインで動く。`claude` コマンドがなければ reader は自動で飛ばされる。

出力は3ブロックに分かれる。textlint の指摘はそのまま直せばよい。rhythm の指摘は数値なので、どこを崩すかは自分で選ぶ。reader の指摘は「読者が詰まった場所」で、最も価値が高い。書き直しの前に目を通し、原文の情報で解消できるものは書き直しに織り込む。解消できないものは、勝手に補わず、最後に「原文の不明点」として返す。

### 2. 決まった順で書き直す

順番には理由がある。先に削らないと、後の工程で直した文が結局消える。語順を直す前に語彙を変えると、語順の判断がぶれる。

1. **削る**。冒頭の「はい、」「もちろんです」「承知しました」。末尾の「いかがでしょうか」「ご確認ください」「〜をお勧めします」「まとめ」節。予告の「以下の通りです」「〜について解説します」。水増しの「非常に」「様々な」「しっかり」。ぼかしの「〜と思われます」「〜かもしれません」「〜と言えるでしょう」は、言い切るか根拠を添えるかのどちらかにする。「〜という」「〜こと」「〜もの」は、削って通じるなら削る。
2. **構造を戻す**。3点セットの箇条書きは、並列で同型の項目が3つ以上あるときだけ残し、それ以外は文に戻す。太字は1段落に1か所まで。「見出し: 説明」の英語式コロンはやめる。一文一義。段落の先頭に主題文を置き、事実と意見を分ける（「ベンチマークで 2.3 倍速い。だから採用すべきだ」）。
3. **語順と読点を直す**。長い修飾語を先に、節を句より先に置く（本多勝一）。読点は「長い修飾語の境界」と「語順が逆のとき」にだけ打ち、「まず、」「そして、」の反射的な読点は減らす。逆接でない「〜ますが、」は句点で切る。「の」の3連続は動詞でほどく（API のレスポンスのバリデーションの処理 → API レスポンスを検証する処理）。従属節の主語は「が」。
4. **語彙を和らげる**。漢語動詞を和語に（実施する → する、実現する → できるようにする、向上させる → 上げる）。「〜を行う」は動詞に戻す。「〜性」「〜化」「〜的」の名詞化は動詞か形容詞に。カタカナ語は定着したものだけ残す（実装、デプロイ、リファクタは残す。ソリューション、インサイト、アプローチ、ロバストは言い換える）。「あなた」「私たち」は削る。日本語は主語を省ける。
5. **リズムを崩す**。同じ文末は2連続まで。文長を短長短で揺らす。体言止めは連続させない。読み上げて息が続かない文は割る。

before → after の一覧は `references/patterns.md` にある。迷ったらそこを見る。

### 3. 意味を変えない

校正は翻訳ではない。原文にない情報を足さない。断定に変えるのは、原文が根拠を持っている場合だけだ。根拠がなければぼかしを残すか、不明点として返す。固有名詞、数値、コード、URL、引用はそのまま。コードブロックの中は触らない。

削りすぎの目安は「読者が失った情報があるか」。挨拶や予告は情報ではないから削れる。「〜の場合は」の条件は情報だから残す。

### 4. 仕上げに機械検査をもう一度

書き直した文章を再びファイルに書き、`check.sh --no-reader` を通す。textlint の指摘が 0 件、rhythm の「同じ文末が3連続」「定型句」が 0 件になるまで直す。文長の変動係数が 0.35 未満なら、まだ均一すぎる。

## 出力

ファイルが対象なら、その場で書き換えて次の要約だけ返す。チャットが対象なら、書き直した本文をそのまま示し、その下に要約を付ける。

```
（書き直した本文）

変更の要点: 冒頭と末尾の定型を削除。「〜することができます」を 4 か所で「〜できます」に。逆接でない「が」を 2 文で句点に。

原文の不明点:
- 「この設定」が何を指すか本文に説明がない
```

「変更の要点」は種類ごとに 1 行、合計 3 行まで。行ごとの diff は出さない。不明点がなければその節は省く。

## 対象外

- 翻訳、英文の校正、要約、加筆
- 意味の変更や主張の追加
- コードそのもの（コード内の日本語コメントは対象にできる）
